# 短跑怎样验收

loss下降是可训练性的证据之一，不能单独证明梯度归约正确。至少检查以下几组独立事实。

| 层次 | 要检查的事实 | 不能由它替代的验证 |
|---|---|---|
| CPU数值 | 完整batch梯度与分片/非均匀/补算梯度一致，Adam步数与参数参考正确 | NPU实际执行、通信、平台作业 |
| 真NPU短跑 | 每作业1张可见卡、HCCL SUM、所有loss/grad有限、每步恰好256样本、重算0 | 长期稳定性或模型效果 |
| 完整状态 | 各卡模型/Adam/config hash一致；最终checkpoint可校验 | 与FP32-master等其他精度轨迹等价 |
| 故障 | 原PID/session保留、原local_grad保护、只补缺失分配、替补先对齐完整状态 | 连续掉卡、任意Adam写入中点恢复 |
| 效果 | 验证集loss或下游任务成绩 | 同协议原生集群对照 |
| 平台收尾 | 自有job全部官方终态，运行/排队/预留0 | 仅本地worker退出 |

toy的固定小模型与确定性数据用于数值和接入验证。CPU oracle比较完整batch梯度与2/3/7分片及补算梯度。真实NPU审计逐步比较global loss和每卡梯度范数，最后对完整参数及Adam状态逐张量比较独立CPU参考；它没有保存每一步所有实际NPU梯度张量。报告初末loss、容差及最终张量最大误差，不能只写“精度正确”。损失下降不要求每一步严格单调。

对于自定义模型，adapter的checkpoint_call_count需要接入者真实维护，不能把默认0当作无重算的独立证明。OpenPI已有禁用与调用拦截；toy前向源码不调用checkpoint。其他模型若直接使用函数式torch.utils.checkpoint，应在自己adapter中禁用并仪器核验该路径。

## 性能口径

首步包含设备初始化/编译等冷启动。分别报告：提交到完成总时长、加载时间、去掉预热后的controller真实commit间隔，以及worker的前反向/数据/归约/更新时长。故障、入组、保存与全状态hash单列，不在正常步均值里隐去，也不要用正常步均值估算全部耗时而不加这些开销。

异步collective入队时间不等于通信完成时间；计时需等待work和设备同步。跨机器未校准的绝对时间不能直接相减当作精确传输时延。跨rank阶段最大值可能来自不同rank，不能随意相加作为关键路径。

toy的模型和梯度很小，控制文件与协议开销可能占大部分时间。它检验“他人能按接口接入并完成训练”，不能代表OpenPI或其他大模型的多卡吞吐。要检验目标模型的速度，使用真实参数量、dtype和通信payload，保持global batch、精度、优化器与数据一致。

## 通信变慢时

先确认真实数据通路、分配布局和参与者是否正常。用同一批卡、同一payload与rank顺序做参数A→B→A对照，每轮新建组并核验输出；预热和最终设备等待都要纳入正确口径。对当前RoCE路径，RDMA_TIMEOUT16与12的同卡往返实验曾出现约6.5秒与1.4秒的整轮差异；这定位到可操作参数，但没有证明所有慢速都由timeout造成。

还需测非2次幂成员、掉卡后的恢复与精度。只测固定64卡纯通信不等于通过63卡恢复。不要把HCCL_RDMA_TIMEOUT的指数编码与心跳秒数混为一谈。

## 失败与收尾

保留失败run及最早错误。停止时先按launcher的cleanup流程处理自己的作业；不删除全局registry、不批量停止账号下所有作业、不修改别人的共享环境。成绩只有在最终状态、数值和资源收尾证据齐全后发布。
